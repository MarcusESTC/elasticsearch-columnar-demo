Columnar Logs / Metrics — Demo Script

Cut version (12 min): Skip Act 2 (Analytics Race) and Act 4 (Search). Run Slides 1–5 → Act 1 → Slides 6–7 → Act 3 (dashboards only, skip PromQL) → Act 5.

Slides 1–4  ~5 min

Slide 1 — Title

"So what we're looking at today is basically: what happens when you don't need a second system for analytics? Elasticsearch has always been great for search and investigation — the question is whether you also have to run something like ClickHouse or BigQuery next to it for the analytics workloads. This is Elastic's answer to that."

Slide 2 — The problem

"So you're already using Elasticsearch for logs — which means when something goes wrong, you're searching in Kibana. But your metrics are in Grafana, on a separate Prometheus stack. So the actual on-call workflow is: alert fires, you go to Grafana to look at the metric, then you switch to Kibana to look at the logs, and you're manually correlating between two systems with two query languages and two time axes. That friction is the problem this is solving."

Slide 3 — What's new

"Columnar Mode is what makes consolidating metrics into Elasticsearch practical. Instead of storing each field multiple ways, you store it once — as a column. That gets you the storage efficiency and query speed that metrics workloads need, without giving up anything on the logs side. And everything you already have — Kibana dashboards, alerts, integrations — keeps working. You change one line when you create the index. Nothing else."

Slide 4 — Columnar Logs

"The first flavor of this is Columnar Logs, which is built specifically for log data. The one thing it keeps from the traditional approach is a full-text index on the message field — because being able to search log messages is the whole reason you'd use Elasticsearch over a warehouse in the first place. Everything else — host names, IPs, ports, rule names — goes columnar. One setting to enable it."

Slide 5 → Act 1 · Storage Footprint  ~4 min

→ Advance to Slide 5 (numbers load live from the demo server)

"I want to be clear that this slide is not canned. These numbers are loading right now from the actual cluster. We took 150,000 realistic firewall log events — wide schema, lots of fields, the kind of data that gets expensive — and ingested the exact same documents into three different index configurations."

Point to the bars:

"Standard mode — the default you'd have today — is about 125 MB. LogsDB, which Elastic already ships and is actually the default on serverless, gets that down to around 44 MB. And Columnar Logs gets it to about 20 MB. That's an 84% reduction from standard, on real data."
"If you're retaining 90 days of logs today, that math means you could keep a full year for the same cost."

→ Switch to http://localhost:8787 · scroll to the top

The stat tiles at the top show the headline numbers live from the cluster. Scroll down slightly to the bar chart to show the three modes side by side — hover a bar to see the exact size.

"Same documents, same schema, same queries. One setting is the only difference between these three bars."

Act 2 · Analytics Race  ~3 min

→ Scroll down to the "Columnar Logs · analytics query race" section

"Okay so the storage savings are real, but the obvious question is: do you pay for it somewhere else? Let's find out — I'll run the same query against all three modes at once and we can compare the results."

→ Select "Top talkers by bytes transferred" from the dropdown · click Run race

Three latency bars appear and the result table loads below.

"Same rows, same order, same numbers. The query engine doesn't know or care what the storage mode is — it just gets answers back. And columnar is actually fast here because scanning columns is exactly what this kind of aggregation wants to do."

"You can run any of these — it's the same story each time. Your dashboards, your queries, your alerts — none of that has to change."

→ Advance to Slide 6

"So that's the logs storage story. But the bigger thing for you is metrics — because this is where you'd actually be consolidating. Elasticsearch rebuilt the time-series storage engine on columnar foundations, which means it's now genuinely competitive with Prometheus on both query speed and storage efficiency. And — this is the important part — you don't have to change anything on the Grafana side to move there. We'll show that."

"This is asking: across the whole 24-hour window, which host had the biggest peak? fw-iad-03 should be at the top. Previously you'd need a dedicated metrics store to run this kind of query efficiently. Now it's in the same cluster as your logs."

Act 4 · Full-Text Search  ~2 min

→ Switch to http://localhost:8787 · scroll to the "Columnar Logs · full-text search" section

"Quick one before the agent demo — this is the reason you'd want logs staying in Elasticsearch rather than moving them somewhere else. Search."

→ Click Search (pre-filled with "DENY ssh"), or type "TLS handshake"

"Highlighted results, individual log events, fast. Your Grafana stack can't do this — it has no concept of full-text search over log messages. Elasticsearch keeps a search index on the message field even when everything else goes columnar. So when your metrics in Elasticsearch show a spike and you want to immediately search the related logs — that's one platform, no context switch."

Act 5 · AI Agent (Agent Builder)  ~8 min

→ Open Kibana · AI Assistant · Agent Builder

"So this is where it gets interesting for me. Everything we've seen so far is the storage and query layer. But what I think is the really compelling story is what happens when you put an AI agent on top of all of it — and the data doesn't have to move anywhere to make that happen."

Walk through the configuration (~2 min)

→ Click into "NetOps Assistant"

"This is a custom agent I set up on top of the same cluster. Agent Builder is Kibana's built-in way to do this — you give the agent a system prompt and register tools it can call. Tools are things like pre-defined ES|QL queries, index searches, or Workflows."

→ Open the Tools tab

Walk through each tool briefly:

  • netops_host_surge_investigation — queries the 24h metrics for a specific host. Takes a host name as a parameter, so the agent can pass in whatever host came up in the conversation.
  • netops_firewall_log_search — full-text search against the columnar log index. This is the one that would be missing if we were using a warehouse-based agent.
  • netops_deny_pattern_analysis — aggregates deny events by rule and protocol. No parameters — the agent just calls it when the question is about what's getting blocked.
  • netops_capacity_outlook — queries the long-term metrics index, the 395-day dataset we just saw in the Year Ahead dashboard, enriched with datacenter and owner info.
"The description on each tool is literally what the model reads to decide whether to call it. That's the interface between you and the LLM — get the description right and the agent picks the right tool. Get it wrong and it either calls the wrong thing or hallucinates."

→ Show the Configuration tab (system instructions)

"The system prompt tells the agent what indices exist, what the schema looks like, and how to frame answers. I also put the talking point in there — that all four tools query the same cluster. So the agent reinforces that narrative in its responses, which is a nice bonus."

Demo conversations (~6 min)

→ Open a conversation with the agent

Tip: Responses take 20–40 seconds. Narrate what's happening in the reasoning trace while you wait — it makes the wait feel intentional.

Prompt 1 — Incident triage:

→ Type: "Which host had the biggest traffic surge, and what are the top rules being denied?"

"One question, two completely different data sources — metrics and logs. Watch the reasoning trace."

As tools fire:

"It's deciding what to call, calling some things in parallel, and then using those results to figure out what to dig into next. Multiple queries, orchestrated by the model, against the same cluster."

When the response arrives:

"It led with the most interesting finding, backed it with numbers, and suggested what to look at next. That's useful in an investigation — the agent is basically driving the next step for you."

Prompt 2 — Log search:

→ Type: "Search the logs for geo-block-highrisk events on fw-iad-03"

"Now I'm asking it to search — the thing a warehouse-based agent can't do. It's going to use the full-text search tool against the columnar index."

When results arrive:

"Individual log events, highlighted matches. Same index we ran aggregations against two minutes ago. This is the part that requires Elasticsearch — you can't do this with just a columnar store."

Prompt 3 — Capacity planning:

→ Type: "What's the capacity outlook across the fleet, and which hosts should we be worried about?"

"This one goes to the Year Ahead dataset — the 395-day index we saw in the dashboard. The agent will join in host metadata automatically."

When results arrive, point to the datacenter/owner/environment columns:

"Those extra columns — datacenter, environment, owner — that's the enrichment from the lookup table, inside the same query. The agent didn't go to a second system to get that. Everything is in Elasticsearch."
"So that's the full picture. Your logs are already in Elasticsearch. Metrics can move here without changing your Grafana setup. Once they're in the same place, you get correlation, search, and AI assistance across both — and that last demo shows what that actually looks like in practice. That's the story."
