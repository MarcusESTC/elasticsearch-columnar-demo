The problem

Analytics at log scale has meant running a second system

  • Columnar warehouses — ClickHouse, BigQuery, Redshift — win on scan-heavy analytics and storage cost…
  • …but they can't do search: no relevance, no full-text, no needle-in-haystack investigation.
  • So teams run both: double infrastructure, ETL pipelines, data drift, two query languages, two bills.

Why the split existed

Search engines store each field several ways at once — inverted index, doc values, stored fields — to make every query pattern fast. That redundancy is priceless for search and expensive for petabyte-scale telemetry that's mostly filtered, aggregated, and scanned.

What's new

Columnar Mode: store each field once, as columns

  • Fields are stored a single time as doc values — the column store — with no inverted index by default.
  • Index sorting + columnar layout → highly compressible, scan-friendly segments.
  • Same Elasticsearch APIs: ES|QL, aggregations, Kibana, alerts, integrations all keep working.
  • Opt-in per index or template: index.mode: columnar — nothing else changes.

General-purpose columnar analytics, without leaving the cluster your data already lives in.

Purpose-built profile

Columnar Logs: analytics economics, search where it counts

  • First specialized columnar profile, purpose-built for log data.
  • Keeps a single inverted index — on the message field — so full-text investigation stays instant.
  • Everything else — hosts, IPs, ports, rules, metrics — stored fully columnar.
  • Logging defaults: automatic @timestamp, sorted by host.name, @timestamp.
PUT /my-logs
{
  "settings": {
    "index": {
      "mode": "logsdb_columnar"
    }
  }
}

Same architecture, applied to metrics

The new Metrics engine: TSDS rebuilt fully columnar

  • Time-series queries up to 160× faster than earlier TSDS; up to 30× faster than Prometheus on gauge/counter benchmarks.
  • ~3–4 bytes per data point — ~2.5× less storage than Prometheus.
  • Native OTLP ingest (GA 9.3) and Prometheus Remote Write + PromQL (tech preview).
  • New ES|QL TS command: RATE, AVG_OVER_TIME, TBUCKET — counter resets handled correctly.
TS netops-cmp-metrics
| STATS gbps = SUM(RATE(network.in_bytes)) * 8 / 1e9
    BY host.name, t = TBUCKET(30 minutes)
| SORT t

// 86,400 samples · runs live in the demo

Logs get Columnar Logs; metrics get the columnar TSDS engine. Same cluster, same ES|QL, one platform.

Native Prometheus & PromQL — GA

Keep your Grafana dashboards. Migrate the backend.

  • Prometheus remote-write endpoint — point your agents at Elasticsearch; live on this cluster right now.
  • Native PromQL — runs inside the ES|QL engine with the same vectorized, parallel execution. No translation layer to babysit.
  • Migration tool — moves existing Grafana dashboards, alerts, and queries to Elastic. Years of PromQL workflows carry over, not thrown away.
  • AI-ready integrations for Kubernetes and AWS, plus continued storage-efficiency gains.
# your agents:
POST /_prometheus/api/v1/write

# your dashboards:
